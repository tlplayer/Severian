# SIP-0028: CFG Realizations of Shared Blocks

Status: Draft — WIP skeleton
Type: Compiler
Created: 2026-10-03
Target: `sev_compiler/mir/cfg`

## Context

CFG construction turns resolved operations in [MIR](0026-MIR.md) into execution paths. HIR's dependency graph determines compilation grouping; the CFG determines runtime sequencing within a callable realization. Neither replaces source containment.

## Data model

| Component | Contract |
| --- | --- |
| Existing `CfgBody` | Entry index, execution table of shared `Block` records, return type and origin. One body per callable realization. |
| `Block.operations`, `parameters`, `terminator` | Ordered executable operations, incoming values and one explicit exit. Source `contents` remains an index into `BlockGraph.nodes`. |
| Existing `CfgEdge` | Target index within the same body and arguments matching the target's parameters. |
| Existing `CfgTerminator`, `CfgExit` | Resolved control transfer plus originating grammar identity and span. |
| `BlockAddress` and `OperationOrigin` | Source attribution; extend provenance to retain the source-file qualification where only a file-local block ID exists today. |

A source block can produce several execution blocks. These use the same `Block` contract, with separate CFG indices and origins pointing back to the source graph. Source records remain canonical; generated execution records must not masquerade as additional source declarations or be inserted into HIR's SCC partition.

`cfg_index` can change during compaction. Source identity, definition identity and lexical parentage cannot change with it. Execution-table entries refer to canonical execution records, not detached copies that passes update independently.

## Interfaces and flow

Proposed contracts, in pseudocode:

```text
build_cfg(analysis: MirAnalysis, callable: realization) -> CfgBody | diagnostics
verify_cfg(analysis: MirAnalysis, body: CfgBody) -> success | diagnostics
successors(terminator: CfgTerminator) -> edges
```

Resolved syntax providers describe evaluation order and control effects through CFG builder operations. The builder creates branches, joins and exits; it does not switch on source keywords such as `if` or reparse sentence text. New syntax may reuse existing control operations.

Verification checks entry/target validity, terminators, edge argument counts and types, value availability/dominance, return contracts and provenance. Side effects and lazy operands retain their declared ordering. CFG-changing passes update edges and invalidate dependent analyses before [ownership](0027-Ownership.md) runs again.

## Problems to avoid

- Do not treat `SourceBlockId`, `cfg_index` and module membership as interchangeable indices.
- Calls refer to resolved callable identities; they do not create intraprocedural CFG edges into another function's body.
- Shared scopes, recursive dependencies and unreachable source code are not implicit control transfers.
- Unsupported control effects produce diagnostics rather than guessed fallthrough edges.

## Testing

Build from real HIR: nested branches produce a correct join; a loop preserves its backedge and exit; short-circuit operands execute only on the required path. Verify source provenance after splitting/compaction, and reject invalid targets, missing terminators and mismatched edge arguments.

## Open work

Specify callable-to-body indexing, qualified provenance, exceptional/suspension edges and block-parameter construction. Reconcile existing CFG builders around one execution table and shared block contract.
